# Tensor identity evidence in failure paths

Recent CLI forward reports can include `tensor_identity_trace` and per-call `input_tensor_matches`. The worker compares the exact Python `torch.Tensor` object and its PyTorch version counter with earlier recorded module outputs in the same forward. It uses weak references and records paths and invocation IDs, not tensor contents. A clone, an unsupported tensor subclass, or an in-place operation that increments the version counter will not match the earlier output.

A match is only partial observation: it does not prove which module produced the value or reveal operations between module hooks. PyTorch version counters do not necessarily expose every possible mutation (for example, some operations through `.data`). Views, copies, unobserved calls, missing report fields, unsupported containers, bounded traversal/history, and truncation can all hide relationships. An empty match is not proof that no producer exists. The report's `truncated` flag indicates when a tracking limit or unsupported case was encountered; coverage remains partial even when it is false.

The Unix full-screen failure path validates the report's forward, consumer and earlier invocation identities and reported tensor paths before showing candidates. It labels matches as partial, indicates ambiguous registered aliases, and lets the user browse the validated earlier outputs with the left and right arrow keys. Enter opens the selected candidate call; its own validated matches can be followed in turn, and `b` goes back. This follows a chain of partial object matches, not a proven producer chain. Navigation history is limited to 128 hops. The selection is retained separately for each input and when returning from the graph during the same session. The original JSON remains available via `v`.

Press `c` in a call to browse later recorded inputs matching one of its outputs. The default dotted branch diagram and the compact list can be switched with `g`; arrows, Page Up/Down, mouse selection and the wheel navigate them. Each listed input is independently validated through the same report checks, and Enter opens that call at the matched input. The dotted branches depict partial object matches, not proof of consumption, dataflow, or complete fan-out. A maximum of 128 candidate inputs is checked and 128 matching pairs shown; reaching the bound is marked in the list. The worker's own tracking limits can make the report incomplete even when this list does not reach its bound.

Press `F` to return to the structure graph at the current call or the selected later input's module. This selects a registration only when the call has one alias and the inspected graph has exactly one matching path; otherwise the graph leaves its selection unchanged and reports that the location is unknown. The graph identifies the module, not a particular invocation. Press `F` again during the same graph session to restore the local call or branch-list position.

Returning from the later-input list also marks uniquely mapped modules with `?` in the structure graph. In the 2D and exploded layouts, dashed association paths connect visible modules; if the earlier call's module is not on the page, each visible candidate has a `?` continuation at the edge. These paths indicate partial object matches between calls, not proven data flow or exact port connections. Multiple matches are aggregated per module; a match between calls of the same module has a marker but no drawn self-loop. Selecting a marked module shows the count and the earlier call's registration, or “shared call” if that registration is ambiguous. The header marks the projection as partial; `o` hides or shows it. Ambiguous or missing destination registrations are omitted and flagged as limited. The projection is local to this graph session and never adds or changes graph edges.

When a module group has no recorded links, `z` and `x` can still arrange its members in a neutral paged layout. Its header explicitly says no links were recorded, including when `?` marks are visible. The layout and marks do not prove that members are connected.

The line-mode recorded-call details use the same validation to list earlier matching outputs and later matching inputs, including shared-instance ambiguity. A uniquely identified call in the recorded-call list is labeled `@number`; entering that label at the list opens the call even when the current filter would otherwise hide it. A last-observed call absent from the list has no such shortcut. The view states that empty results do not rule out other matches and indicates known truncation. It checks at most 128 input leaves for earlier matches, at most 128 candidate inputs for later matches, and displays at most 128 matches in each direction. This path is also compiled for Windows, but has not been tested in a native Windows terminal.

These matches do not construct graph edges. Historical reports without the fields remain unknown. The original report remains the source of evidence. A proven producer trace and complete consumer graph are not yet implemented.
